3D OPEN-WHEEL RACING SIMULATOR — UPGRADED MASTER DEVELOPMENT PROMPT (v2.0)
0. PURPOSE OF THIS DOCUMENT
This is the single source of truth for designing, engineering, implementing, testing, documenting and shipping a complete browser-based 3D open-wheel racing simulator that runs on GitHub Pages.

You are not building a “3D driving demo”, a toy racer, or a visually impressive but physically fake showcase.

You are building a small but genuine racing simulator with:

physically coherent vehicle behaviour
real setup consequences
tyre, aero, fuel, ERS, damage and weather systems that actually affect the car
a playable first circuit
a professional motorsport UI
a maintainable architecture
graceful performance on low-end integrated graphics
legally clean original assets
zero backend dependency
Every later system must be able to plug into the foundation without rewriting the entire project.

If a feature is shown in the HUD, telemetry, garage, setup screen or race director, it must exist in the simulation. Never fake a system merely to claim it exists.

5. DESIGN PHILOSOPHY
Simulator, not arcade
The car must have mass. It must transfer weight. It must understeer, oversteer, lock, spin up, wash out on grass, gain stability from downforce at speed, and become nervous if the rear wing/floor is damaged or the rear tyres overheat.

Accessible, not elitist
The player can choose:

Casual
Simulation
Hardcore
The underlying vehicle model should remain the same family of systems. Assists and simplifications wrap the model. Do not maintain three unrelated physics engines.

Honest systems
If the HUD shows:

ERS 62%
tyre wear 43%
rear wing open
brake temp 780°C
fuel 48.2 kg
front wing damage 35%
then those values must be consumed by the simulation that frame.

One-car, one-track foundation first
Do not drown v0.1 in championship trees, particle luxury, or photo mode. First make the car drive around a real lap with timing, camera, collision, HUD and repeatable physics.

Expand, don’t rewrite
All systems should be data-driven where possible:

tracks in JSON

upgrades in JSON

quality presets in config
rules in config
6. TECH ARCHITECTURE PRINCIPLES
Separate ticks
Never couple everything to requestAnimationFrame naively.

Implement three clocks:

Physics tick — fixed, e.g. 120 Hz internal or 60 Hz on Low, with accumulator
Render tick — variable, interpolated
UI tick — 10–30 Hz for most HUD numbers, higher only for RPM/speed needle if needed
Use interpolation between previous and current physics states for smooth rendering.

Determinism goal
Full lockstep determinism is not required for v1, but:

use fixed dt for physics
avoid random gameplay events during physics integration except through a seeded RNG
keep a seeded random for weather/AI incidents so a session can be reproduced in debug
Memory and CPU budget for HD 4400
Suggested starting budgets (Low):

under ~250–400 draw calls
under ~150k–300k triangles on screen if possible
textures mostly 256–512, a few 1024
one fullscreen canvas
audio voices capped
AI cars: 0 in v0.1–0.5, then 4–11 with aggressive LOD
no per-frame GC spikes from allocating vectors
Use object pools for:

particles
audio sources
AI decision scratch data
telemetry samples
collision events
vector/quaternion math if not using pooled Three.js patterns carefully
